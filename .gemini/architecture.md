# Архитектура системы

В данном документе описывается архитектурный каркас клиентского приложения **websolutions**, спроектированный для эффективной работы с асинхронными данными, локализацией и многоуровневым роутингом.

---

## 1. Хранилища состояния (Pinia Stores)

Управление состоянием в приложении разбито на специализированные слои. Особое внимание уделено предотвращению дублирования запросов и разделению контекстов блоков.

### 1.1 `uiStore` (Синглтон)
Хранит глобальное состояние интерфейса, активный языковой/раздельный префикс (`scope`), а также метаданные текущей страницы.
* **`scope`**: URL-префикс раздела (например, `'ru'`, `'en'` или пустая строка `''`). См. подробнее в [Правилах и Конвенциях](conventions.md).
* **`isGlobalLoading`**: Геттер, отслеживающий состояние активных запросов по счётчику `_loadingCount`.
* **`buildPageVars`**: Строит хлебные крошки (`breadcrumbs`), определяет `title`, `key`, `parent` и `children` на основе структуры навигации, текущей категории и просматриваемого элемента.

### 1.2 `navigationStore` (Синглтон)
Отвечает за структуру навигации и меню.
* **`structure`**: Дерево подразделов и услуг, загружаемое по slug.
* **`nav`**: Массив нормализованных ссылок для рендеринга главного навигационного меню (`navbar`).
* **`fetchNavigation(scope)`**: Подгружает ссылки меню под конкретный `scope`. Запросы делаются параллельно с контентом страниц и оптимизированы для исключения повторного скачивания при переходах.

### 1.3 `blockStore(id)` (Фабрика на уровне модуля)
**Ключевое архитектурное решение.** Данное хранилище не является синглтоном. Оно создаёт изолированные инстансы хранилища для каждого блока на странице по уникальному `id`. Это решает проблему совместного использования стора на разных страницах, когда данные одного блока могли перезаписать данные другого.
* **Реестр сторов:** Определение стора кэшируется внутри модуля в `Map`. При повторном вызове `useBlockStore(id)` возвращается уже существующий инстанс Pinia Store для этого `id` (например, `block/portfolio`, `block/services`).
* **Методы:**
  * `fetchBlockCategory(slug)`
  * `fetchBlockItem(slug)`
  * `fetchOverlayCategory(slug)`

## 2. Оркестрация жизненного цикла компонентов (`usePageOrchestrator`)

Связующим звеном между Pinia, Vue Router и презентационными компонентами является композиция `usePageOrchestrator`. Она берёт на себя всю логику по загрузке данных, управлению мета-тегами (через `@unhead/vue`) и вычислению переменных контекста страницы.

### 2.1 Сигнатура вызова
```js
const { blockStore, navigationStore } = usePageOrchestrator(blockId, scheme, {
  fetch: (route) => slug // Функция-резолвер для получения slug из роута
})
```

### 2.2 Схемы загрузки (`scheme`)
Параметр `scheme` указывает оркестратору, какие именно уровни данных нужно загрузить последовательно.
* `'category'` — загрузка категории блока (`fetchBlockCategory`).
* `'item'` — загрузка конкретного элемента блока (`fetchBlockItem`).
* `'structure'` — загрузка дерева навигации (`fetchStructure`).
* `'structure+category'` — последовательная загрузка структуры и категории.
* `'structure+category+item'` — последовательная загрузка всех трех сущностей.

### 2.3 Автоматическое определение владельца страницы (`isPageOwner`)
Контекст хлебных крошек и заголовка страницы в `uiStore` должен обновляться (`buildPageVars`) только один раз для главной сущности страницы. Оркестратор автоматически вычисляет признак `isPageOwner`:
```js
const isPageOwner = route.name === blockId || route.params.slug === blockId
```
Если оркестратор вызывается во вложенном блоке (например, блок `portfolio` рендерится внутри главной страницы `Home.vue`), `isPageOwner` будет `false`, и хлебные крошки главной страницы не будут повреждены данными портфолио.

### 2.4 Защита от дублирующихся запросов
Внутри файла `usePageOrchestrator.js` на уровне модуля объявлена структура `_activeKeys` (`Map`).
Каждый запрос маркируется ключом `${blockId}::${slug}::${uiStore.scope}`. Если ключ совпадает с текущим активным, повторный вызов функции `load()` блокируется. Это предотвращает двойные запросы при быстром переклике страниц, навигации назад, а также во время двойного монтирования компонентов в режиме разработки.

## 3. Управление глобальной загрузкой (Global Loading)

Для того чтобы избежать дёргания интерфейса и показывать один общий прелоадер для всех параллельных асинхронных запросов, `uiStore` реализует механизм счётчика:
* Любой асинхронный экшен, инициирующий запрос к API, вызывает `startGlobalLoading()`, что инкрементирует `_loadingCount`.
* По завершении (успешном или с ошибкой) вызывается `stopGlobalLoading()`, декрементирующий счётчик (с ограничением снизу на `0`).
* Геттер `isGlobalLoading` возвращает `true` только пока `_loadingCount > 0`.
